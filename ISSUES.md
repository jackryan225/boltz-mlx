# Upstream issue audit: jwohlwend/boltz and ml-explore/mlx

Audited 2026-10-27 from public GitHub list/search pages and a few issue/PR pages (no gh CLI, no login).
Caveat: list pages show titles only, so some summaries below are inferred from titles. Items marked (title-only) were not opened.
Port baseline: boltz 2.2.1 @ b1ebfc4, mlx 0.32.4, host is Apple M5 Pro, macOS 26.6.2.

## Boltz

### Mac / MPS / CPU

- https://github.com/jwohlwend/boltz/pull/527 (open) and https://github.com/jwohlwend/boltz/pull/231 (open): community MPS support PRs, never merged upstream. Reports: runs on M1 Max 64 GB and M3 Max; only fallback seen was `aten::linalg_svd` at `model/loss/diffusionv2.py:51` (weighted_rigid_align, verified in local clone) (CPU fallback, fixed natively in torch 2.14 nightlies); 16 GB Macs limited to ~350 residues; macOS `libomp` duplicate crash ("OMP: Error #15").
  Implication for port: `linalg_svd` is used in the rigid/Kabsch alignment (weighted_rigid_align). MLX has `mx.linalg.svd` (CPU stream only), so use a CPU stream there, or replace it with a 3x3 closed-form or Newton-Schulz polar decomposition. Keep memory budget in mind: ~350 residues was the practical limit on 16 GB under torch.
- https://github.com/jwohlwend/boltz/pull/652 (closed, author opened it in the wrong repo): MPS support claims forced float32 on MPS, single device. Benchmark claim: M3 Air about 1.1-2.0x slower than a T4.
  Implication for port: gives a rough speed target. Torch MPS reference runs should be forced to fp32.
- https://github.com/jwohlwend/boltz/issues/653 and https://github.com/jwohlwend/boltz/issues/662 (closed via PR #670, commit 63000a7, which is already in b1ebfc4): `torch.autocast("cuda", enabled=False)` did not disable autocast on CPU, so diffusion sampling, diffusion training and affinity ran in bf16. Result: distorted structures with long bonds and clashes, and confidence 0.86-0.88 on CPU vs 0.91-0.93 on GPU.
  Implication for port: the reference must run these blocks in fp32. The local clone has the fix (`autocast_device_type` in `modules/utils.py`, used at `boltz2.py` lines 533/572/629). Reference dumps made with an older checkout or `--accelerator gpu` in bf16-mixed are NOT a valid fp32 oracle. Generate oracle tensors on CPU fp32 (or MPS fp32) from b1ebfc4. Diffusion sampling and the confidence/affinity heads should be fp32 in MLX.
- https://github.com/jwohlwend/boltz/issues/275 and PR #276 (closed): trifast was Linux-only, which broke Mac installs; fixed by making it a Linux-only dependency.
  Implication for port: the Mac reference path is the pure-PyTorch einsum triangle code (`--no_kernels`). Do not depend on cuequivariance or trifast for oracles.
- https://github.com/jwohlwend/boltz/issues/625 (closed, title-only): `--accelerator cpu` not working. https://github.com/jwohlwend/boltz/issues/535 (closed, title-only): process killed on CPU for the example files.
  Implication for port: expect the CPU oracle for large inputs to be slow and memory-heavy. Use small cases for the oracle, and dump per-module activations rather than full runs.

### Numerics, kernels, fallbacks

- https://github.com/jwohlwend/boltz/issues/391 (closed as not planned): "kernels degrade 4090" was not reproduced. A contributor ran 100 monomers: with a fixed seed, cuequivariance and `--no_kernels` were nearly identical. Kernels were 1.43x faster. Differences without a fixed seed were seed noise.
  Implication for port: the PyTorch fallback is the reference. Per-layer parity should be tight (fp32 ~1e-5 relative). End-to-end RMSD comparisons need matched noise/seeds, or must be judged statistically.
- https://github.com/jwohlwend/boltz/issues/452 (closed as not planned): cuequivariance triangle-attention kernel illegal memory access (`run_fmha.cu`) for sequences over ~250 residues in one report. Users also hit Triton errors: #485, #433, #395, #638.
  Implication for port: not an MLX issue, but avoid taking the kernel path as the oracle for long sequences. Our port implements the mathematical definition (fallback semantics).
- https://github.com/jwohlwend/boltz/pull/681 (closed) / https://github.com/jwohlwend/boltz/pull/682 (open, never merged; fork `fnachon/boltz` merged it Jul 2026): bundles 4 fixes: (1) kernel ImportError/RuntimeError falls back to einsum; (2) `pre_affinity_{id}.npz` check (#390); (3) potentials softmax underflow fix (#621); (4) dead code. Also adds `--flash_attn` SDPA.
  Implication for port: item 3 is a real inference-output change that upstream still has. The local `potentials.py` lines 76-87 and 143-164 use `exp(-lambda*energy)/Z` with `Z==0 -> 0`, which underflows in fp32 and silently zeros the union-potential energy and gradient. Decide explicitly: port the upstream behaviour for parity (default) and optionally add the max-shifted softmax behind a flag. Document which one the tests assert.
- https://github.com/jwohlwend/boltz/issues/621 (open): contact restraints (`force: true`) often not enforced. Linked to the same underflow fix in #682.
  Implication for port: if potentials are ported, parity vs upstream will reproduce the same weak steering. Do not "fix" this silently.
- https://github.com/jwohlwend/boltz/issues/553 and PR #554 (closed/merged, Aug 2025, already in b1ebfc4): MSA dropout in bf16 dropped ~0.2% of rows even at dropout=0 (`torch.rand` in bf16 hits exactly 0).
  Implication for port: dropout must be a no-op at inference (skip the RNG path entirely). In bf16/fp16 MLX, avoid threshold tests on low-precision random values.
- https://github.com/jwohlwend/boltz/issues/428 (closed as not planned): `--use_potentials` crashed on CPU with "index put dtype mismatch Float vs BFloat16" at `potentials.py` ~133.
  Implication for port: another symptom of unintended bf16 in the potentials path. Run potentials in fp32.
- https://github.com/jwohlwend/boltz/issues/644 (closed as not planned): report that `boltz2_conf.ckpt` is missing `pairformer_module.layers.*.attention.norm_s.*` (128 tensors) relative to latest main. Unconfirmed, and may be specific to a newer fork. A community fork also added `**kwargs` to `AtomDiffusion.__init__` for extra hparams such as `mse_rotational_alignment`.
  Implication for port: the converter should load strictly and report missing/unexpected keys explicitly. Never fall back to random init silently. Verify against b1ebfc4's own `state_dict`.
- https://github.com/jwohlwend/boltz/pull/524 (merged Aug 2025, already in; "attn_bug_fix") and commit ab3b088 (cyclic_period padding): earlier fixes already in b1ebfc4 (title-only).
  Implication for port: nothing to do; just confirm the local source has them.

### Determinism / reproducibility

- https://github.com/jwohlwend/boltz/issues/636 (open): CASP16 affinity Pearson R reproduces ~0.52 vs paper 0.65. Lead: the molecular-weight correction is on in the model class but off by default in the CLI (`--affinity_mw_correction`). Same-seed GPU runs differ at ~0.03 in affinity value.
  Implication for port: define the affinity parity target as "same as upstream CLI defaults" (no MW correction). Expose the flag. GPU torch is not bitwise reproducible, so use tolerances, not equality.
- https://github.com/jwohlwend/boltz/issues/594, #459, #253, #78 (closed): seed and consistency questions. A fixed `--seed` does not give identical outputs across different inputs, and MSA subsampling is a separate RNG.
  Implication for port: separate the RNGs (MSA subsample, diffusion init noise, per-step noise, augmentation). For parity tests, inject noise tensors dumped from torch rather than reseeding `mx.random`, since the streams differ.
- https://github.com/jwohlwend/boltz/issues/627 (closed): MSA caching degraded predictions.
  Implication for port: always regenerate features for test cases; do not reuse stale MSA caches.
- https://github.com/jwohlwend/boltz/issues/710 (open): cyclic D-peptide gets wrong stereochemistry. Chirality constraints only take effect with `--use_potentials`.
  Implication for port: chirality and bond-geometry potentials matter for ligand quality. If we skip potentials, document it as a known gap.

### javierbq/boltz-mlx

- https://github.com/javierbq/boltz-mlx exists (MIT, 7 commits, 0 stars, no releases). It is an MLX **Swift** port of Boltz-2 trunk, diffusion and sampler with int8 group-64 quantization, targeting iOS and macOS.
  Claims, unverified: module-boundary Pearson r >= 0.9997 vs PyTorch, structure passes a 2.0 A / 0.9 lDDT gate "at adequate diffusion-step counts", 529 MB int8 model, 3-13 s per small protein on iPhone 15 Pro, 0.6-1.4 GB peak.
  Explicitly out of scope: confidence head, affinity, potentials, training. Needs upstream boltz for features and weight export.
  Implication for port: no overlap with our full-feature goals (confidence and affinity). Its Pearson-per-module parity idea is a good metric to copy, but note that 0.9997 is a weak bar for fp32. Do not reuse its code without reading it first.

## MLX (0.32.x; mx.config only on main)

- https://github.com/ml-explore/mlx/issues/3860 (closed, docs) and docs PR https://github.com/ml-explore/mlx/pull/3894 (merged): on Apple M5-generation (gen-17+) GPUs with macOS 26.2 or later, float32 matmul-family ops (matmul, conv, attention, and ops lowered to them such as einsum) may run at TF32-class precision by default. Measured relative error: 2^-10.4 on a 512^3 matmul, 1.9e-3 on an outer product, 4.3e-2 max absolute error on a batched (48,64,128)@(48,128,32). `MLX_ENABLE_TF32=0` restores full fp32 (about 2.5-3x slower matmul and about 2x slower attention in one report). M3 and earlier are unaffected.
  Implication for port: **our host is an M5 Pro, so this applies**. For every parity test against torch fp32, set `MLX_ENABLE_TF32=0`. Production can opt back in per op (see mx.config). The env var is read once at the first relevant op, so set it before importing or running anything (`os.environ[...]` first line). Record the TF32 setting in every results table. This is the most likely cause of unexplained 1e-3 diffs in triangle-mult einsums and pair attention.
- https://github.com/ml-explore/mlx/pull/4647 (merged 2026-10-27, after 0.32.4) and https://github.com/ml-explore/mlx/issues/4595 (closed): adds `mx.config.update("MLX_ENABLE_TF32", 0)` and `with mx.config.scoped_update(MLX_ENABLE_TF32=0):`. #4595 shows fp32 conv3d on M5 about 5000x less precise (rel err 6.4e-3), and Winograd conv selection depends on batch size.
  Implication for port: 0.32.4 does not have `mx.config`, so use the env var, or move to a build with #4647 for scoped control (for example, fp32 for triangle/outer-product ops and TF32 for big linear layers). If any convs are used (Boltz has none in the trunk, except possibly in distogram/embedding paths), beware Winograd/batch dependence.
- https://github.com/ml-explore/mlx/pull/4641, #4613 (merged), https://github.com/ml-explore/mlx/pull/4769 (open, "Fix premature rounding in addmm"), #4760: bf16/fp16 accumulation issues were found in split-K quantized matmul and `addmm` (premature rounding).
  Implication for port: avoid `mx.addmm` in bf16 paths until #4769 lands, or verify. Prefer separate fp32-accumulated matmul + bias. If using bf16 weights, compare against a fp32 oracle per layer.
- mx.fast.scaled_dot_product_attention (docs): additive mask must "promote to" the q/k/v dtype and be broadcastable to [B, N, Tq, Tkv] (max 4 dims). A boolean mask is also accepted. Softmax is computed in fp32. Release notes: 0.32.4 fixes negative-stride mask handling (#4650) and a missing stream in the fallback (#4663). Fused kernels have been extended across head dims 72, 96, 256 and 512 (#4330, #4499, #4416, #4459). `force_fused=True` (#4185) raises if no fused kernel exists.
  Implication for port: Boltz attention uses small head dims and a pair-bias additive term. Test each attention site (pairformer AttentionPairBias, triangle attention, diffusion transformer, atom attention windows) against the fp32 oracle with `force_fused=True` and `False`. Confirm which head dims hit the fused path in 0.32.4. Use large negative finite values (not -inf) in masks, and make the bias dtype match q.
- https://github.com/ml-explore/mlx/issues/2835 (closed; causal mask alignment with S_Q != S_KV) and https://github.com/ml-explore/mlx/issues/1842 (closed; no QxQ mask): "causal" is lower-right aligned. Not relevant to Boltz (no causal masks) beyond windowed atom attention.
  Implication for port: windowed atom attention should pass explicit masks, not rely on "causal".
- https://github.com/ml-explore/mlx/issues/4759 (open) / PR #4772 (open): Metal `layer_norm` writes out of bounds for narrow rows (16/64 wide). Outputs matched in the reporter's tests, but this is undefined behaviour, and rows of 16-64 are 14-70x slower than 256.
  Implication for port: Boltz LayerNorms are 128/384/768/... wide; the 16/64 widths are not used much (check any head-dim LN or `c_hidden=32`). If a narrow-row norm shows up, use an explicit mean/var implementation. Pin and re-test on upgrade.
- https://github.com/ml-explore/mlx/pull/4461 (merged, 0.32.3): compiled and eager sigmoid now agree (`precise::exp`). Related: #4511 fixed float constant precision in compiled kernels.
  Implication for port: before 0.32.3, `mx.compile` could change sigmoid or SiLU numerics. 0.32.4 is fine, but keep compile on/off parity tests, and do not mix MLX versions when comparing results.
- mx.compile gotchas: https://github.com/ml-explore/mlx/issues/3940 and #4096 (closed; compiled fn could return another function's result when released off its tracing thread), #3672 and #3813 (closed; shapeless compile elided size-1 reductions and broke dynamic-batch matmul), #3932 (closed; multi-output leak), #3338 (closed; compile gave wrong results for an unsigned to signed astype feeding matmul).
  Implication for port: do not use `shapeless=True` for the trunk (the sequence length is dynamic). Compile per bucket of padded lengths, or compile only fixed-shape blocks. Always diff compiled vs eager outputs. Single-threaded use only.
- mx.fast.metal_kernel limitations (title-only unless noted): https://github.com/ml-explore/mlx/issues/3832 (closed; same-name kernels with different sources ran stale code in one eval batch), #3347 and #3461 (closed; use-after-free and buffer lifetime under lazy graphs), #4534 (closed; dispatch silently truncated because group dims are clamped to grid dims), https://github.com/ml-explore/mlx/issues/4603 (open; MathModeSafe wrong rows on M3 Ultra/macOS 27), #2547 (closed; no read+write inputs), #4541 (closed; no offline .metallib).
  Implication for port: for the later Metal phase, give each kernel a unique name, check that the dispatch grid >= the threadgroup size, keep inputs read-only (write via outputs), and compare against the Python reference. Use fast-math "Relaxed" mode with care, and test it on the M5.
- Memory: https://github.com/ml-explore/mlx/issues/4609 (closed; wired memory released when the GPU goes idle), #3350 (closed; the caching allocator can keep unbounded buffers), #3830 (closed; ~5 s GPU watchdog on long single command buffers), #3186 (open; kernel panic on huge prefill), #3849 (closed; Metal resource limit query). Controls: `mx.set_memory_limit`, `mx.set_cache_limit`, `mx.set_wired_limit`, `mx.clear_cache`; `MLX_MAX_OPS_PER_BUFFER` and `MLX_MAX_MB_PER_BUFFER` can be changed per section via mx.config (#4647).
  Implication for port: Boltz pair tensors are O(N^2 * 128) (N=1000 gives ~512 MB per fp32 pair tensor, with several live at a time). Plan chunking over the pair dimension in triangle ops (as torch does). Call `mx.eval` at block boundaries to bound the graph and keep command buffers short. Call `mx.clear_cache()` between recycling iterations. Record `mx.get_peak_memory()`. Run long jobs below the ~5 s watchdog per command buffer by splitting evals.
- bf16/fp16 reductions: https://github.com/ml-explore/mlx/pull/4387 (0.32.3; CPU fp16/bf16 reductions now accumulate in fp32), #4291 (arg-reductions propagate NaN), #4146 (median NaN). No sigmoid, softmax or layer_norm numerics bugs were found beyond the items above.
  Implication for port: CPU-stream results for half types changed at 0.32.3. Keep oracle comparisons in fp32. NaN behaviour in argmax/argmin is now propagating, so check the distogram and pLDDT bin logic.
- einsum: https://github.com/ml-explore/mlx/pull/4125 and #4124 (fixed 0.32.x; size-1 batch dims not broadcast when the smaller operand is first), #4299 (dropped trailing empty subscript), #4463 (integer contractions pick an unsupported matmul path).
  Implication for port: Boltz triangle-mult einsums ('bikd,bjkd->bijd' etc.) are float and use batch dims. Confirm fixes are in 0.32.4 (the 0.32.2 release notes list #4299), and prefer an explicit `matmul` with transposes for the hot paths. That also lets us control TF32 and precision.
- Not found: any MLX issue specific to SDPA with additive bias NaNs, or with fp32 bias shapes like [B,H,N,N] at large N. Treat as unknown and test.

## Action items

1. Set `MLX_ENABLE_TF32=0` (before first op) in all parity and benchmark scripts. Log it, and compare TF32 on vs off on the triangle-mult and pair-attention tests. Consider moving to a build with `mx.config` for scoped control.
2. Regenerate all torch oracles from b1ebfc4 in fp32 on CPU/MPS (autocast fix #670 included). Never use bf16-mixed GPU dumps. Use `--no_kernels` semantics for triangle ops and attention.
3. Implement diffusion sampling, confidence and affinity in fp32. Inject dumped noise for parity tests instead of matching RNG streams.
4. Port the potentials softmax exactly as upstream (with the underflow behaviour), and leave a flagged max-shifted variant plus a test documenting the difference (#621, #682).
5. Converter: strict key checking against b1ebfc4's `state_dict`, with explicit failure on missing `norm_s` (#644) or unexpected hparams. Never random-init silently.
6. Use `weighted_rigid_align` SVD on the CPU stream (or a custom polar decomposition). It is the one op torch MPS also falls back on.
7. Attention: test each site (head dim, bias shape and dtype) against the fp32 oracle with `force_fused` on and off. Use finite negative masks.
8. Memory plan: chunk pair ops, `mx.eval` at block boundaries, `mx.clear_cache()` between recycles, set memory and wired limits, and record peak memory per case.
9. Do not use `mx.compile(shapeless=True)` on the trunk. Compare compiled vs eager. Avoid `mx.addmm` in bf16 until #4769 is verified.
10. For the Metal phase, unique kernel names, explicit grid/threadgroup checks, read-only inputs, and a pinned MLX version. Avoid narrow-row layer_norm (#4759).
11. Re-read javierbq/boltz-mlx (Swift, int8, no confidence/affinity) only for ideas on parity fixtures. Re-check the upstream commits page for anything after b1ebfc4 before each milestone.

## Round 2 audit (fp16 / NAX), 2026-10-27

Sources: public github.com pages only. Dates are PR/issue dates as shown. 0.32.4 was released 2026-10-14; anything merged after that is marked POST-0.32.4 (unusable). Items marked (title-only) or (page summary) were not verified in source. Verified-locally items say so.

### A. Round 1 items, re-read for fp16

- #3860/#3894/#3953/#3897/#4411 (TF32, all closed "expected"): the reduced-precision path is fp32-only. #4411's reporter found fp16/bf16 results bit-identical with and without `MLX_METAL_GPU_ARCH=applegpu_g14p`; #3897 found fp16 SDPA diverging ~2^-11 on M5 (the fp32 part was TF32). Implication for round 2: fp16 GEMM has no TF32-style extra loss; its error is the fp16 output rounding (rel 2^-11 per element). Compare the fp16 path against the strict fp32 build, not against TF32.
- #4769 (OPEN, updated 2026-10-27): addmm premature rounding fixes GEMV/GEMVT and the split-K transform (bf16 example 1.0 vs 1.0078125); dense GEMM already uses accumulator-typed transforms. Implication for round 2: keep "never addmm in fp16". Also do not rely on `x@W + b` fusing into one op; M=1 and split-K shapes take other paths. The grep test stays.
- #4613 (closed, fixed in 0.32.4 as #4641): split-K quantized matmul partials kept in input dtype. Implication for round 2: quantized only; irrelevant to fp16 dense weights, but do not mix in quantized paths.
- #4759/#4772 (OPEN): `layer_norm_single_row` writes `thread_x[-232..-1]` for rows of 16/64/264 (fp16 benchmarks, outputs correct as tested). Implication for round 2: Boltz LN widths (128/256/384/768) are fine, but a fp16 LN over 24/32/48-wide head data or 264 would hit it. Do not add LN over narrow rows; use an explicit fp32 mean/var there.
- #4461 (0.32.3) / #4511: compiled vs eager sigmoid now agree. Implication for round 2: fp16 casts inside `mx.compile` are fused; still diff compiled vs eager for every fp16 block.
- #4387 (0.32.3): CPU fp16/bf16 reductions accumulate in fp32. Implication for round 2: matches the policy "L1 numbers from GPU only"; CPU fp16 is not a proxy for NAX.
- #4534, #3832, #3347/#3461, #4603, #2547, #4541 (metal_kernel): see section D for what changed; #4603 is a bfloat-arithmetic compiler bug. Implication for round 2: do arithmetic on `half` in float where it matters; keep unique kernel names and read-only inputs.

### B. New ml-explore/mlx: GEMM accuracy / NAX / Metal 4

- https://github.com/ml-explore/mlx/blob/v0.32.4/mlx/backend/metal/kernels/steel/gemm/nax.h (read at tag v0.32.4): NAX frag `mma` uses `mpp::tensor_ops::matmul2d` (descriptor 16x32x16, `multiply_accumulate`, `execution_simdgroup`) from `<MetalPerformancePrimitives/MetalPerformancePrimitives.h>`. `A/B/C` types are separate template params; `gemm_nax.h` defaults `AccumType = float`; tiles are loaded and stored with per-element `static_cast`. Implication for round 2: a kernel with half in / float out is expressible (a `NAXTile<float,...>` stored to `device float*`), but the stock fused kernels store `T`. This supports the SPEC claim (verified from the file; no half/float instantiation seen).
- https://github.com/ml-explore/mlx/pull/4640 (merged 2026-10-08, listed in the 0.32.4 notes with #4654 thin-M): thin-N NAX GEMM (32x32 per simdgroup, K split across 4 simdgroups, B via mpp); bf16 benchmarked on M5 Pro; precision not discussed. Implication for round 2: for N <= ~64 GEMMs (pair bias heads `Linear(c_z, 16)`, gating) the kernel changed between 0.31 and 0.32.4: re-measure fp16 error and speed for those shapes (K-split means a different summation order).
- https://github.com/ml-explore/mlx/issues/3797 (closed 2026-07-07, PR #3810): bf16 `steel_gemm_splitk_axpby_nax` returned garbage in JIT builds (wrong type param); AOT wheels fine. Implication for round 2: we use the AOT wheel (fine). If we ever JIT the NAX headers via `header=`, instantiate the dtype explicitly and bit-check against `mx.matmul` at load (the sys1rust PR #29 does exactly that).
- https://github.com/ml-explore/mlx/issues/4720 (OPEN), #4198 (closed): `qmm_splitk` is chosen over `qmm_nax` on M5 for M=16-64 (quantized only). #4676 (closed): `test_qmm_splitk_precision` fails on gen-17+. Implication for round 2: quantized-only; but it shows dispatch heuristics for M<=64 differ on M5. Time fp16 GEMM at the small-M shapes (diffusion token path, M ~ N tokens) rather than extrapolating from large-M.
- https://github.com/ml-explore/mlx/pull/4682, #4692, #4712, #4722, #4734, #4723, #4725, #4717 (all merged/open between 2026-10-18 and 10-26, POST-0.32.4): staged affine qmm NAX, qmv_nax 6-16 rows, int8 qmm, sliding-window attention, `sdpa_split` mid rows, split of row-kernel launches over 2^32 threads. Implication for round 2: none usable. Note #4624/#4717: softmax/layer_norm/rms_norm return zeros at >= 2^27 rows with last axis <= 128 (fp16 included); 0.32.4 is affected. Boltz pair tensors are 2^20 rows at N=1000, so not reached.
- https://github.com/ml-explore/mlx/issues/2693 (closed 2025-10-22): Metal 4 tensor API support "is a work in progress"; no public API. #4594 (merged 2026-09-30, in 0.32.4): "cooperative tensor build issues on macOS 27". #4597 (closed): `gated_delta_update_nax.h` failed to compile on the macOS 27 SDK. Implication for round 2: NAX/mpp kernels compile on macOS 26.6; a newer SDK/toolchain can break JIT'd header code, so pin the OS and record `xcrun metal --version` in the jsonl.
- External evidence (not mlx): https://github.com/nyosegawa/speech.cpp/issues/153 (page summary): `matmul2d` with half operands from device memory and float accumulation reached 62-65 TFLOP/s on M5 Max vs ~14 for `simdgroup_matrix`; https://github.com/krishhgg/sys1rust/pull/29: MLX's NAX headers (`steel/gemm/nax.h`, `gemm_nax.h` and 3 more, from 0.32.2) are inlined into one `metal_kernel` header string with `#pragma once` and `#include "mlx/..."` lines stripped, gated on macOS >= 26.2 and arch gen >= 17, and checked bit-exact vs `mx.matmul`. Implication for round 2: this is the recipe for step 5 (fp16-in/fp32-out). Expected ceiling is the NAX rate; a plain `simdgroup_matrix<half>` kernel is the 6.3 TFLOP/s case. Unverified by us; test the header route first.
- https://github.com/ml-explore/mlx/issues/3592 and PR #3728 (merged 2026-07-07, so in 0.32.4): `mx.fast.metal_kernel` gained a math mode (`"safe"` default, `"relaxed"`, `"fast"`); the docs example is `compile_options={"math_mode": "relaxed"}` (check the exact spelling in 0.32.4 before use). #4553 (closed 2026-09-24, no PR link seen): `safe`/`relaxed` still compiled bare `exp/log/pow` as `fast::` (about 30 ULP vs 1.4 ULP for `precise::exp`, fp32 test). Implication for round 2: in custom kernels call `metal::precise::exp` explicitly for softmax/sigmoid and test `exp(-large)`; do not assume the default is precise.

### C. New ml-explore/mlx: attention, softmax, norms in fp16

- https://github.com/ml-explore/mlx/pull/4416 (merged 2026-09-02) and #4455, #4499, #4330, #4459: fused NAX SDPA for head dims 64/72/80/96/128/256/512 (array masks for 256 since #4416). The fused path accumulates in fp32; the fallback materializes the score matrix in fp16 before softmax (the author measured the fused path ~3x closer to an fp32 reference). Implication for round 2: Boltz head dims are 24 (pairformer s, 384/16), 32 (triangle attention), 48 (diffusion 768/16): by this list NONE hit a fused kernel, so SDPA in fp16 means the unfused fallback with fp16 scores. Inference from the head-dim list; run `force_fused=True` once per site to confirm. Keep SDPA in fp32 per policy, or pad head dim to 64 with zeros (exact for QK^T and for PV after slicing; scale must stay `hd**-0.5`).
- https://github.com/ml-explore/mlx/issues/3658 (closed by #4185): `force_fused=True` raises if no fused kernel exists. Mask must promote to the q/k/v dtype per the docs. Implication for round 2: an fp16 additive mask must be finite-safe: Boltz uses `-inf=-1e6` (`attention.py:124`, `attentionv2.py:103`, verified locally), which is -inf in fp16 (max 65504). Use -1e4 if added in half, else add in fp32.
- No MLX issue was found on fp16 SDPA NaNs for fully-masked rows or -inf additive masks (searched; related: #2626, #1248, #2126, all non-NaN). Implication for round 2: unknown, so test it: all-masked rows (padding tokens) in fp16 with -1e4 vs -inf.
- https://github.com/ml-explore/mlx/issues/4718 (closed by #4719, 2026-10-19, POST-0.32.4): fp16 head_dim 256 SDPA 2-pass vector crashed on M1/M2 (threadgroup limit). Implication for round 2: M1/M2 only, not our host.
- https://github.com/ml-explore/mlx/issues/3585 (closed, no fix): fused SDPA differs from manual attention by up to 0.33 in fp32 on M4; maintainer: not bitwise-identical by design. Implication for round 2: parity tests for SDPA need tolerances, not equality.
- https://github.com/ml-explore/mlx/issues/4228, PR #4230 (merged 2026-08-22): `nn.InstanceNorm` fp16 variance overflowed to inf for finite inputs (|x|=512); the fix routes through `mx.fast.layer_norm`. Implication for round 2: do not use `mx.var`/`mean(x*x)` on fp16 data (hand-written norms overflow at |x| ~ 256); only `mx.fast.layer_norm`. The Metal LN kernel's accumulation dtype was not checked in this audit; test fp16 LN with |x|~500 once.
- https://github.com/ml-explore/mlx/issues/4220 (closed): `nan_to_num` replaced inf by 0 instead of the dtype max in fp16. Implication for round 2: do not use `nan_to_num` as an overflow guard; count with `isinf | isnan` as in the policy.
- https://github.com/ml-explore/mlx/pull/4626 (0.32.4): fixed fp16 overflow in `clip_grad_norm`. Implication for round 2: none (training).

### D. mx.fast.metal_kernel facts that matter

- Docs (v0.32.4 `custom_metal_kernels.rst`) do not describe `header=`; they say only `mlx/backend/metal/kernels/utils.h` is auto-included. Whether a user `#include "mlx/backend/metal/kernels/..."` resolves is NOT documented; third-party code avoids it by inlining. Implication for round 2: test `#include` once; otherwise inline headers as sys1rust does.
- #4004 (0.32.4, "Metal extension build support") and #4541 (closed: no precompiled-metallib API; maintainer points to math mode). Implication for round 2: no offline `-Ofast` path in 0.32.4; custom kernels are runtime-compiled.
- #4603 (OPEN): native `bfloat` vector arithmetic returned wrong rows under `safe` math on M3 Ultra/macOS 27 (not seen on M2 Max/macOS 26.6). Implication for round 2: cast `half` to `float` before accumulating vector sums, and diff each custom kernel against MLX on the M5 under the OS we ship.

### E. jwohlwend/boltz

- https://github.com/jwohlwend/boltz/blob/b1ebfc4/src/boltz/model/layers/triangular_mult.py (lines 116/119 and 204/207, verified in the local clone): `a, b = torch.chunk(x.float(), 2, dim=-1)` then `torch.einsum("bikd,bjkd->bijd", a, b)`. There is no `autocast` in this file. The trunk (PairformerModule, MSAModule) is NOT inside a `torch.autocast(enabled=False)`; only the pairformer `s` stack (`pairformer.py:105`), the template-distogram code, the diffusion and the confidence heads are. Training uses `precision="bf16-mixed"` (`main.py:1262`). I tested on CPU (torch 2.14.1, bf16 autocast): fp32 inputs to this einsum give a bf16 OUTPUT with rel err 3.1e-3 vs fp64 (1.0e-7 without autocast). The CUDA case works through the same `bmm` autocast rule but was not run. Implication for round 2: the `.float()` precedent is a bf16-operand, bf16-output GEMM (fp32 accumulate, bf16 range, 8 mantissa bits). It is NOT evidence that the contraction is safe in fp16. bf16 has fp32 range; fp16 does not. Our fp16 triangle-mult needs its own ACT_RANGES evidence; do not cite upstream as precedent for range.
- Same file, trunk-level: the mask multiply `x * mask` precedes the cast and the tri-mult output goes straight into `norm_out`, so upstream's real accumulation is over k in fp32 but the output is rounded to bf16 per element (2^-9). Implication for round 2: a fp16 output (2^-11) is finer than upstream's GPU bf16 default, so "fp16 error vs strict" should be compared with bf16-mixed error as a calibration, if a bf16-mixed oracle is cheap to produce on CPU.
- https://github.com/jwohlwend/boltz/pull/264 / #263 (closed, not merged): `--use_cuda_bfloat16`; Boltz-2 already runs `bf16-mixed`; reporter saw no accuracy loss on ~6 PDBs; bf16 was 3-8x slower on CPU/MPS; maintainer wanted extensive testing.
